# Расчётное ядро бота питания — спецификация v1.2

Документ описывает детерминированную часть системы: расчёт нормы, распределение БЖУ, алгоритм подбора плана, ограничители безопасности и схему данных.

**Принцип:** всё, что описано в этом документе, считается кодом. Модель к расчётам не допускается. ИИ работает только на входе (разбор текста) и на выходе (формулировки, выбор из готовых вариантов).

**Изменения v1.2 (22 сентября 2026):** верхний допуск по жирам из 5.3 в коде отсутствовал — реализован, цена измерена; в `score` добавлен штраф за отклонение жиров (5.4); пункт про жиры убран из расхождений 5.7.

**Изменения v1.1 (22 сентября 2026):** блюдо может подходить к нескольким приёмам пищи (5.2); добавки описаны как часть алгоритма (5.6); схема данных приведена в соответствие (раздел 8); зафиксированы расхождения версии 1 со спецификацией (5.7).

## 1. Профиль пользователя

### 1.1 Собираемые параметры

| Поле | Тип | Валидация |
|---|---|---|
| `sex` | enum | `male` / `female` |
| `age` | int | 18–90 |
| `height_cm` | int | 130–230 |
| `weight_kg` | float | 35–250 |
| `activity` | enum | см. 2.2 |
| `goal` | enum | `cut` / `maintain` / `bulk` |
| `target_weight_kg` | float | опционально |
| `meals_per_day` | int | 3–5, по умолчанию 4 |
| `exclusions` | array | аллергии, непереносимости, «не ем X» |

### 1.2 Стоп-условия онбординга

Бот **не рассчитывает норму** и мягко направляет к специалисту, если:

- `age < 18`
- ИМТ < 18.5 при цели `cut`
- целевой вес даёт ИМТ < 18.5
- пользователь указал беременность или грудное вскармливание
- указан диагноз, требующий лечебной диеты (диабет, ХБП, целиакия и др.)

Формулировка отказа — без осуждения, с объяснением, что персональный расчёт в этих случаях должен делать врач или диетолог.

**ИМТ** = `weight_kg / (height_m ²)`

## 2. Расчёт нормы калорий

### 2.1 Базовый метаболизм (Миффлин — Сан Жеор)

```
Мужчины:  BMR = 10×вес + 6.25×рост − 5×возраст + 5
Женщины:  BMR = 10×вес + 6.25×рост − 5×возраст − 161
```
Вес в кг, рост в см, возраст в годах.

### 2.2 Коэффициент активности

| Значение | Множитель | Описание для пользователя |
|---|---|---|
| `sedentary` | 1.2 | Сидячая работа, тренировок нет |
| `light` | 1.375 | 1–3 тренировки в неделю |
| `moderate` | 1.55 | 3–5 тренировок в неделю |
| `high` | 1.725 | 6–7 тренировок в неделю |
| `athlete` | 1.9 | Физический труд + тренировки |

```
TDEE = BMR × activity_multiplier
```

### 2.3 Корректировка под цель

| Цель | Корректировка | Ожидаемый темп |
|---|---|---|
| `cut` | −15% (по умолчанию), допустимо до −20% | 0.5–0.8% массы тела в неделю |
| `maintain` | 0% | стабильно ±0.3 кг |
| `bulk` | +12% | 0.25–0.4% массы тела в неделю |

```
target_kcal = round(TDEE × (1 + adjustment), -1)
```

Агрессивный дефицит (−25% и глубже) не предлагается никогда, даже по запросу.

### 2.4 Ограничители (применяются после расчёта)

Порядок проверок:

1. `target_kcal ≥ BMR` — норма не опускается ниже базового метаболизма
2. Абсолютный пол: **1200 ккал** для женщин, **1500 ккал** для мужчин
3. Если после ограничителей дефицит меньше 8% — цель `cut` недостижима безопасно, предложить `maintain` и рекомпозицию

Каждое срабатывание логируется и объясняется пользователю простым языком.

## 3. Распределение БЖУ

### 3.1 Расчётный вес

При ИМТ > 30 расчёт нутриентов от фактического веса завышает цифры. Используется скорректированный вес:

```
если ИМТ ≤ 30:  calc_weight = weight_kg
если ИМТ > 30:  ideal = 22 × height_m²
                calc_weight = ideal + 0.25 × (weight_kg − ideal)
```

### 3.2 Белок

| Цель | г на кг `calc_weight` |
|---|---|
| `cut` | 2.0 |
| `maintain` | 1.5 |
| `bulk` | 1.8 |

Верхний предел — 2.5 г/кг, выше смысла нет.
`protein_g = calc_weight × coef` → `protein_kcal = protein_g × 4`

### 3.3 Жиры

```
fat_g = calc_weight × 0.9
минимум: calc_weight × 0.8
дополнительный минимум: не менее 20% от target_kcal
```
`fat_kcal = fat_g × 9`

Нижняя граница жёсткая — жиры ниже неё нельзя урезать ради углеводов.

### 3.4 Углеводы — остаток

```
carb_kcal = target_kcal − protein_kcal − fat_kcal
carb_g = carb_kcal / 4
```

**Проверка:** если `carb_g < 100`, пересобрать — снизить белок до 1.6 г/кг, затем жиры до минимума. Если и после этого углеводы ниже 100 г, значит норма слишком низкая: вернуться к шагу 2.4.

**Порядок проверен, менять не нужно.** Резать белок раньше жира выглядит спорно: для человека, который начал тренироваться, белок — последнее, что стоит урезать. Замер на сетке из 130 профилей: пересборка срабатывает у 8, все женщины на дефиците, нормы 1200–1850 ккал. Альтернативный порядок («держать белок 2.0 г/кг, резать жир до минимума») спасает белок только у **одного** из восьми — у остальных углеводы всё равно проваливаются ниже 100 г. То есть в подавляющем большинстве случаев места действительно нет и белку приходится уступить.

Для профиля «невысокая женщина, ИМТ 21, сидячая работа, дефицит» (1240 ккал) альтернатива сработала бы. Но правильный ответ для неё — не менять порядок, а добавить тренировки: уже при 1–3 тренировках в неделю норма поднимается до 1430 ккал и белок держится на 2.0 г/кг без всякой пересборки.

### 3.5 Дополнительные ориентиры

- Клетчатка: 14 г на каждые 1000 ккал
- Вода: 30 мл на кг фактического веса

## 4. Распределение по приёмам пищи

Для 4 приёмов (завтрак / обед / ужин / перекус):

| Приём | Доля калорий | Доля белка |
|---|---|---|
| Завтрак | 25% | 25% |
| Обед | 35% | 30% |
| Ужин | 30% | 30% |
| Перекус | 10% | 15% |

Белок распределён ровнее калорий — это влияет на синтез мышечного белка.

Для 3 приёмов: 30 / 40 / 30. Для 5 — добавляется второй перекус, доли обеда и ужина уменьшаются на 5 п.п. каждая.

## 5. Алгоритм подбора плана

### 5.1 Фильтрация базы

Перед перебором из базы исключаются рецепты, содержащие продукты из `exclusions`, и рецепты, встречавшиеся у пользователя за последние 2 дня.

### 5.2 Перебор

Комбинация = по одному рецепту на каждый приём пищи. Для каждой комбинации подбираются индивидуальные коэффициенты порций.

**Мультиприём.** Блюдо не привязано к одному приёму: у рецепта есть список приёмов, к которым оно подходит (например, `lunch,dinner`). Пул слота — все рецепты, у которых этот приём в списке. **Одно блюдо ставится в день только один раз**: комбинации с повтором отбрасываются. На базе из 18 рецептов это подняло покрытие в 6–14 раз.

**Границы масштабирования:**

```
scale ∈ [0.75, 1.40], шаг 0.05
рецепты с флагом is_fixed_portion: scale = 1.0
```

### 5.3 Допуски попадания

| Показатель | Допуск |
|---|---|
| Калории | ±5% или ±75 ккал (что больше) |
| Белок | не ниже −5%, не выше +15% |
| Жиры | ±20%, но не ниже минимума из 3.3 |
| Углеводы | свободно (остаточный показатель) |

**Верхняя граница по жирам обязательна, и вот почему.** До 22 сентября 2026 код проверял только нижнюю границу: `fat < fat_g * 0.8` отбрасывало план, а сверху жир был не ограничен вовсе. Замер на 130 планах показал последствия:

| Показатель | Без верхней границы | С допуском ±20% |
|---|---|---|
| Жиры, медиана от нормы | 1.40 | 1.01 |
| Жиры, 90-й процентиль | 1.90 | 1.16 |
| Жиры, максимум | 2.91 | 1.20 |
| Углеводы, медиана от нормы | 0.77 | — |

Механика простая: калории и белок зажаты допусками, жир свободен, а углеводы — остаточный показатель, и они схлопываются жиру навстречу. Поэтому «свободно» в строке про углеводы работает только при закрытом коридоре по жирам.

**Цена соблюдения.** На базе из 80 позиций допуск ±20% даёт покрытие 98.5% против 100% без верхней границы: два профиля из 130 (атлеты на наборе, нормы 3800 и 3870 ккал) остаются без плана. Это предпочтительнее плана с жиром в полтора раза выше нормы: для таких случаев есть 5.5. Правильное решение — калорийные блюда с низкой долей жира в базе, а не расширение допуска.

### 5.4 Ранжирование подходящих вариантов

```
score = 100
      − 15 × (штраф за повтор рецепта за последние 5 дней)
      − 10 × (повтор основного белкового продукта внутри дня)
      −  5 × |scale − 1.0| × 100   (сильно растянутые порции хуже)
      −  0.5 × |жиры/норма − 1.0| × 100   (отклонение по жирам)
      +  8 × (совпадение с предпочтениями пользователя)
      +  5 × (укладывается в лимит времени готовки)
```

Топ-5 по `score` передаются в ИИ-слой, который выбирает финальный и пишет текст.

**Штраф по жирам** добавлен в v1.2. Он не влияет на покрытие: набор допустимых планов тот же, меняется только порядок. Внутри допуска ±20% он подтягивает медиану с 1.16 до 1.01. Коэффициент 0.5 — наименьший дающий эффект: при 10% отклонения он стоит 5 очков и не перебивает штраф за повтор блюда (15). Побочный эффект на растяжку порций ничтожен: средняя |scale − 1| выросла с 0.005 до 0.014.

Углеводы отдельно не штрафуются: как остаточный показатель они выправляются сами, когда закрыты коридоры по калориям, белку и жирам.

**Предпочтения (`prefer_tags`).** Бонус +8 за каждое блюдо с совпавшим тегом. Механизм проверен на сетке из 54 профилей «невысокая женщина»: без предпочтений десерт попадает в план в 50% случаев, с `prefer_tags=["десерт"]` — в 100%. В данных для этого размечены теги `десерт` (17 позиций) и `сладкое` (25). Онбординг предпочтения пока не спрашивает, `profiles.prefer_tags` остаётся пустым — механизм готов, но не включён.

### 5.5 Отсутствие решения

Если ни одна комбинация не проходит допуски: расширить границы масштабирования до `[0.7, 1.5]`, затем снять фильтр повторов. Если решения всё равно нет — сообщить, что база рецептов слишком мала для этой нормы, и предложить ближайший вариант с указанием фактического отклонения.

### 5.6 Добавки

Добавка — гарнир или дополнение к порции, которое автор выносит припиской «к порции, в КБЖУ не входит»: хлеб, крупа, картофель, банан, йогурт. Хранится отдельно от рецептов (таблица `addons`), у каждой — КБЖУ, приёмы, к которым подходит, и уровень `base` / `high`.

К каждой комбинации блюд перебираются варианты добавки, включая «без добавки»; итог дня считается вместе с ней. Строка «без добавки» с нулевой калорийностью обязана существовать в данных: без неё добавка становится принудительной в каждом плане.

**Зачем.** Авторские блюда высокобелковые. Без углеводного слоя мужские нормы не закрываются вовсе (0 вариантов): растягивание порций поднимает калории и белок одновременно, а добавка поднимает калории, разбавляя долю белка. Уровень `high` — крупные гарниры до 550 ккал для высоких норм.

**Предел.** Добавка не спасает, когда белок уже пробит блюдами: для атлета 190/120 (4770 ккал, 161 г белка) не помогают гарниры даже до 1400 ккал. Такие нормы закрываются только небелковыми блюдами в базе. То же теперь верно и про жиры: после закрытия коридора по жирам оставшиеся непокрытые профили упираются не в белок, а в жир, и лечатся калорийными нежирными блюдами.

### 5.7 Расхождения версии 1 со спецификацией

Осознанно отложено:

- масштаб порции общий на весь день, а не индивидуальный на блюдо (5.2);
- допуски проверяются только по итогу дня; доли приёмов из раздела 4 в подборе не контролируются. Замер на 130 планах: доля перекуса в калорийности дня — медиана 13% при заложенных 10%, 90-й процентиль 20%, максимум 26%. Нужны коридоры по приёмам;
- каскад 5.5 в коде другой: сначала снимается учёт повторов, затем добавляется пятый приём; границы масштабирования не расширяются;
- фильтр 5.1 по последним 2 дням не применяется — повторы только штрафуются в `score`;
- время готовки в `score`: вместо бонуса +5 за укладку в лимит — штраф −10 за каждое блюдо сверх лимита;
- перебор комбинаций перестал быть исчерпывающим: при пулах 24/42/39/37 комбинаций 1 454 544 при пороге 60 000, дальше идёт случайная выборка. Результат зависит от `seed`.

**Закрыто в v1.2:** верхний допуск по жирам из 5.3 реализован.

## 6. Пересчёт в течение дня

Сценарий: пользователь съел что-то не по плану.

```
remaining_kcal = target_kcal − consumed_kcal
remaining_protein = protein_g − consumed_protein
```

**Правила:**

- Если остаток ≥ 25% дневной нормы → пересобрать оставшиеся приёмы под остаток тем же алгоритмом
- Если остаток < 25% → не пересобирать. Показать факт, предложить лёгкий вариант, не загонять в минус
- Если норма превышена → **никаких компенсаций**: не урезать следующий день, не предлагать «отработать». Зафиксировать факт нейтрально и вернуться к плану завтра

Последнее правило принципиальное. Механика компенсации — прямой путь к нездоровым паттернам, и в продукте её быть не должно.

## 7. Пересчёт нормы по динамике

Раз в 14 дней, при наличии минимум 8 взвешиваний.

```
avg_now = среднее веса за последние 7 дней
avg_prev = среднее веса за 7 дней двухнедельной давности
rate = (avg_now − avg_prev) / avg_prev / 2   // % в неделю
```

Скользящее среднее нужно, чтобы убрать колебания воды.

| Цель | Целевой коридор | Действие вне коридора |
|---|---|---|
| `cut` | −0.5% … −0.8% в неделю | медленнее → −8% к норме; быстрее → +8% |
| `maintain` | −0.3% … +0.3% | скорректировать на ±5% |
| `bulk` | +0.25% … +0.4% | медленнее → +8%; быстрее → −8% |

После корректировки все ограничители из 2.4 применяются заново.

## 8. Схема данных

```
users
  id, telegram_id, created_at, tz, locale

profiles
  user_id FK, sex, age, height_cm, weight_kg, activity,
  goal, target_weight_kg, meals_per_day, exclusions jsonb,
  target_kcal, protein_g, fat_g, carb_g, calculated_at

products
  id, name, name_normalized, kcal_100, protein_100,
  fat_100, carb_100, source (off/usda/manual)

recipes
  id, title, meals text[], kcal, protein, fat, carb,
  portion_g, is_fixed_portion bool, cook_minutes,
  tags[], steps text, author_id

recipe_items
  recipe_id FK, product_id FK, grams

addons
  id, title, kcal, protein, fat, carb, meals text[], tier (base/high)

plans
  id, user_id FK, date, status, target_kcal_snapshot

plan_items
  plan_id FK, recipe_id FK, meal_type, scale, is_eaten

diary_entries
  id, user_id FK, datetime, source (plan/text/manual),
  raw_text, kcal, protein, fat, carb

weight_log
  user_id FK, date, weight_kg

user_product_cache
  user_id FK, phrase, product_id FK, grams, hits
```

`recipes.meals` — список приёмов, к которым блюдо подходит (5.2). В `plan_items.meal_type` — один конкретный слот, куда блюдо поставлено в этом плане.

`portion_g` — вес **готовой** порции. Сумма сырых ингредиентов его не заменяет: крупы набирают воду, мясо теряет. Пока нет замера — поле пустое.

`user_product_cache` — ключевая таблица для экономии: одна и та же фраза пользователя разбирается моделью один раз, дальше берётся из кэша.

В версии 1 рецепты и добавки лежат в CSV (`data/recipes.csv`, `data/addons.csv`), список приёмов — строкой через запятую.

## 10. Контрольные примеры для тестов

**Женщина, 30 лет, 165 см, 68 кг, `moderate`, цель `cut`**
BMR = 10×68 + 6.25×165 − 5×30 − 161 = 680 + 1031 − 150 − 161 = **1400**
TDEE = 1400 × 1.55 = **2170**
target = 2170 × 0.85 = **1840**
Проверка: 1840 > 1400 ✓, > 1200 ✓
ИМТ = 24.98 → calc_weight = 68
Белок 136 г (544 ккал) · Жиры 61 г (549 ккал) · Углеводы 187 г (747 ккал)

**Мужчина, 35 лет, 180 см, 75 кг, `light`, цель `bulk`**
BMR = 750 + 1125 − 175 + 5 = **1705**
TDEE = 1705 × 1.375 = **2344**
target = 2344 × 1.12 = **2630**
Белок 135 г · Жиры 68 г · Углеводы 370 г

Обе пары воспроизводятся кодом версии 1 точно. Если после правки цифры разошлись — сломано ядро.
