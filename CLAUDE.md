# CLAUDE.md

Контекст репозитория для Claude Code. Читается автоматически в каждой сессии.

## Что это

Telegram-бот, который **планирует** питание на день: по параметрам человека
считает норму калорий и БЖУ и подбирает из базы конкретные блюда с граммовкой.
Не трекер — считает заранее, а не постфактум.

Продукт для широкой аудитории, не для личного пользования. Отсюда требования
к безопасности расчётов ниже — они не формальность.

## Команды

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
export BOT_TOKEN=...        # из .env, в git не попадает
python -m app.bot           # long polling
```

Автотестов нет. Проверка изменений — раздел «Как проверять» ниже.

## Карта файлов

```
app/core.py         нормы, БЖУ, ограничители, стоп-условия. Чистые функции.
app/planner.py      подбор плана: фильтр → перебор → масштаб → допуски → score
app/db.py           SQLite; весь SQL только здесь, остальные модули его не видят
app/bot.py          хендлеры aiogram 3, FSM онбординга
data/recipes.csv    80 позиций (64 авторских рецепта + 16 продуктов)
data/addons.csv     12 добавок
scripts/coverage.py прогон покрытия по сетке профилей
```

Зависимость односторонняя: `bot.py` → `planner.py` → `core.py`, и `bot.py` → `db.py`.
`core.py` не импортирует ничего из проекта — это намеренно.

## Инварианты

Не менять без явного указания человека. Каждый пункт стоит за собой реальную
причину, а не вкусовщину.

**Модель не считает.** Арифметика, подбор, любые цифры — код. ИИ (когда
появится) только разбирает свободный текст и формулирует ответы. В текущей
версии ИИ не используется вообще и зависимостей от него нет.

**Никаких компенсаций.** Превышение нормы не переносится на следующий день,
«отработать» бот не предлагает. Если будете писать пересчёт дня — правило из
спецификации: остаток меньше 25% нормы не пересобирается, превышение
фиксируется нейтрально.

**Полы по калориям.** `KCAL_FLOOR` в `core.py`: 1200 для женщин, 1500 для
мужчин, и норма никогда не ниже BMR. Порядок проверок в `calculate()` важен:
сначала BMR, потом абсолютный пол.

**Стоп-условия.** `check_eligible()` бросает `NotEligible` для
несовершеннолетних, беременности, ИМТ ниже 18.5 с целью снижения, лечебной
диеты. Текст исключения показывается пользователю дословно — он написан
аккуратно, не переписывать мимоходом.

**Авторские рецепты.** `data/recipes.csv` содержит собственный сборник
владелицы проекта — 64 рецепта. Репозиторий приватный: это неопубликованный
контент, который лежит в основе платного продукта. Не выкладывать содержимое
в примеры, не коммитить в публичные форки.

**Секреты.** `BOT_TOKEN` только в переменных окружения. `.env` и
`data/bot.db` в `.gitignore` — не убирать.

## Как работает подбор

Ломается легче, чем кажется, поэтому коротко о механике.

1. `filter_recipes()` убирает рецепты с исключёнными продуктами.
2. Перебор: по одному рецепту на каждый приём пищи. Блюдо может подходить
   к нескольким приёмам — колонка `meals` в CSV, список через запятую
   (`lunch,dinner`). Пул слота — все рецепты, у которых этот приём в списке.
   Комбинации с одним и тем же блюдом дважды за день отбрасываются.
3. **Добавка** (`addons.csv`) — гарнир или дополнение «к порции, в КБЖУ не
   входит». Не украшение: подборка высокобелковая, и без углеводного слоя
   мужские нормы не закрываются **вообще** — ноль вариантов. Добавка
   разбавляет долю белка; растягивание порций такого эффекта не даёт.
   Строки с `tier=high` существуют именно для этого. Строка `a00` с нулевой
   калорийностью — это «без добавки», не удалять: иначе добавка станет
   обязательной в каждом плане.
4. Масштабирование порций 0.75–1.40; `fixed=1` не масштабируется.
5. Допуски: калории ±5% (но не меньше ±75 ккал), белок от −5% до +15%,
   жиры не ниже 80% нормы.
6. `score` ранжирует прошедшие варианты: штраф за повтор блюда из последних
   пяти дней, за сильно растянутую порцию, за два одинаковых белковых
   продукта в дне; бонус за совпадение с предпочтениями.
7. `relax_and_build()` — каскад при отсутствии решения: снять учёт повторов,
   затем перейти на пять приёмов пищи.

`_combos()` перебирает комбинации исчерпывающе, пока их не больше 60 000,
и переходит на случайную выборку того же размера, когда база вырастает.
Проверки идут на числах, объекты `PlanItem` строятся только для прошедших
допуски — без этого подбор занимал секунды.

**Текущая база уже за этим порогом.** Пулы 24/42/39/37 дают 1 454 544
комбинации, то есть подбор видит около 4% пространства. Это ожидаемо и не
ошибка, но означает: результат зависит от `seed`, «лучший план» не
гарантирован, а сравнивать прогоны можно только при одинаковом seed.

## Конвенции

- Русский язык в строках интерфейса и комментариях, английский в коде.
- Формулы и коэффициенты — только именованные константы наверху `core.py`.
  Магических чисел в теле функций быть не должно.
- `core.py` остаётся без побочных эффектов и без импортов проекта: его
  функции должны вызываться в тестах без БД и без Telegram.
- Весь SQL — в `db.py`. Хендлеры не знают о схеме.
- Новые строки интерфейса не должны содержать `_ * [ ] \`` — Telegram
  парсит их как Markdown и падает с `can't parse entities`.

## Как проверять изменения

Контрольные примеры. Если после правки цифры разошлись — сломано ядро.

```bash
python3 -c "
from app.core import Profile, calculate, NotEligible
from app.planner import *
t = calculate(Profile('female',30,165,68,'moderate','cut'))
assert (t.bmr, t.tdee, t.kcal) == (1400, 2170, 1840), (t.bmr, t.tdee, t.kcal)
assert (t.protein_g, t.fat_g, t.carb_g) == (136, 61, 187)
t2 = calculate(Profile('male',35,180,75,'light','bulk'))
assert (t2.bmr, t2.kcal) == (1705, 2630)
try:
    calculate(Profile('female',16,165,55,'light','cut')); raise SystemExit('стоп-условие не сработало')
except NotEligible: pass
R, A = load_recipes(), load_addons()
for p in [Profile('female',30,165,68,'moderate','cut'), Profile('male',35,180,75,'light','bulk')]:
    tt = calculate(p)
    plans, _ = relax_and_build(tt, filter_recipes(R, []), A, meals=4, seed=1)
    assert plans, 'план не собрался'
    assert abs(plans[0].kcal - tt.kcal) <= max(tt.kcal*0.05, 75)
print('ядро и подбор в порядке')
"
```

Покрытие после изменений базы:

```bash
python3 scripts/coverage.py --n 130
```

Отдельно вручную в Telegram: `/start` → `/plan` → «Другой вариант» → `/profile`
→ `/delete`. Мужской профиль с целью «набрать» обязан выдавать строку «К этому»
— если её нет, сломан механизм добавок.

## Состояние базы

Измерено `scripts/coverage.py` на сетке из 130 профилей (seed 20260922):

| Состав | Покрытие |
|---|---|
| 34 позиции (партия 1 + продукты) | 73.8% |
| 80 позиций (партии 1–4 + продукты) | **100%** |

Пулы по приёмам: завтрак 24, обед 42, ужин 39, перекус 37. Разброс
калорийности внутри каждого приёма выше целевых 2.00. Пустых полос
калорийности нет.

**Что в базе требует сверки с первоисточником.** Партии 2–4 рассчитаны по
составу и надёжны. А вот:

- у партии 1 (`id` вида `p1-*`) КБЖУ перенесены из проектной документации,
  а `fixed`, `tags` и `allergens` проставлены по названиям — их стоит
  сверить с авторскими карточками;
- 16 продуктов (`pr-*`) и 12 добавок (`a*`) собраны по справочным значениям,
  а не взяты из готового файла. КБЖУ правдоподобные, но состав набора
  выбран заново.

Пока это не сверено, цифра покрытия — оценка, а не факт.

## Известные ограничения версии 1

Осознанно отложено, не чинить попутно.

- Масштаб порции общий на весь день; в спецификации заложен индивидуальный.
  Это первая доработка после запуска.
- Подбор проверяет только итог за день, а не распределение по приёмам.
  На высоких нормах перекус может выйти на 1000+ ккал при нормальном обеде.
  Суммы верные, раскладка неудачная. Лечится коридорами по приёмам.
- SQLite на эфемерном диске Railway стирается при редеплое. Переход на
  PostgreSQL: `psycopg`, `?` → `%s`, `AUTOINCREMENT` → `GENERATED BY DEFAULT
  AS IDENTITY`, `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING`. Меняется
  только `db.py`.
- Вес порции у авторских рецептов пустой: сумма сырых ингредиентов не равна
  весу готового блюда. Не заполнять расчётом — нужны замеры на кухне.
  Пока поле пустое, бот показывает «порция ×коэффициент» вместо граммов.
- Обед и ужин закрыты почти одним пулом: только пять блюд из 64 привязаны
  к одному слоту. Следствие мультиприёма, сделано намеренно.
- `cmd_replace` использует seed от даты, поэтому даёт один и тот же
  «другой вариант» в течение дня.
- Нет дневника, разбора текста, напоминаний, витрины подборок, оплаты.

## Чего не делать

- Не переписывать стек. Python + aiogram 3 + Railway выбраны осознанно.
- Не добавлять ИИ-вызовы в расчёты или подбор.
- Не запускать бота локально, пока он работает на Railway: два процесса с
  одним токеном дают `TelegramConflictError`.
- Не смягчать ограничители и стоп-условия «для удобства тестирования».
  Для тестов достаточно подставить другой профиль.
- Не «чинить» потолок по белку +15% и не расширять допуски, если план не
  собирается. Это данные базы, а не код.
